# «На виду»

**Обращения жителей многоквартирного дома в мессенджере MAX**

Решение подготовлено командой MAXITO для хакатона «Умный город». Название репозитория и внутренние технические идентификаторы (MAXITO) относятся к команде; наименование самого продукта — «На виду».

## 1. Назначение решения

Жители всё активнее переходят на цифровые каналы взаимодействия (+20%), отмечая, что так удобнее оставлять обращения. Однако это не сделало процесс прозрачнее: 50% заявителей, оставивших оценку, не удовлетворены ответом. При этом поток жалоб продолжает расти (+50% за год), а 57% обращений оказываются повторными. В результате сигнал о действительно значимых проблемах теряется, управляющая компания перегружается, а доверие жителей падает.

С 1 сентября 2026 года взаимодействие управляющих организаций с собственниками и пользователями помещений через мессенджер MAX прямо предусмотрено правилами управления многоквартирными домами (ПП РФ от 26.01.2026 № 40).

«На виду» переносит весь процесс — от подачи обращения до его закрытия — внутрь MAX. Житель фиксирует проблему по структурированной форме и видит её статус на каждом этапе. Управляющая компания получает обращения в едином виде, с приоритетом по числу поддержавших жителей, вместо разрозненных звонков и сообщений.

## 2. Где и для кого используется решение

Решение работает полностью внутри мессенджера MAX, в формате чат-бота с подключённым мини-приложением. Один развёрнутый экземпляр решения обслуживает одну управляющую компанию; в структуре управляющей компании может быть несколько домов.

Распределение ролей в решении соответствует фактическому распределению обязанностей при управлении многоквартирным домом: содержание общего имущества и организация работы с обращениями жителей относятся к обязанностям управляющей организации (ст. 161–162 Жилищного кодекса РФ), при этом управляющая организация на практике включает административное звено и аварийно-диспетчерскую службу, непосредственно работающую с жителями. Этому распределению в решении соответствуют три роли.

**Представитель управляющей компании**

Сотрудник управляющей компании с административными полномочиями или ответственный, назначенный из числа диспетчеров. Вносит дома (адрес, число подъездов, этажность, год постройки, ссылка на общий чат жителей), загружает списки диспетчеров и жителей, указывает реквизиты управляющей компании и номера аварийных служб, распределяет дома между диспетчерами.

**Диспетчер**

Сотрудник аварийно-диспетчерской службы, закреплённый за одним или несколькими домами. Принимает и обрабатывает обращения жителей своих домов, меняет их статус, публикует плановые уведомления о временных отключениях коммунальных услуг или неработоспособности общего имущества.

**Житель**

Собственник или наниматель помещения в доме. Сообщает о проблемах, отслеживает статус своих обращений, поддерживает лайком обращения других жителей дома, получает уведомления о плановых работах, просматривает информацию о доме и управляющей компании.

Самостоятельная регистрация в решении не предусмотрена ни для одной роли: доступ диспетчерам и жителям открывает Представитель управляющей компании, заранее внося их данные в систему. Исключение — демонстрационный вход по кодовому слову, который включается только на время проверки (см. раздел 7).

## 3. Основной пользовательский сценарий

Приоритетный сценарий описан для роли «Житель» — участника процесса, для которого существует система обращений.

1. Житель впервые открывает бота «На виду» в MAX и передаёт боту свой контакт.
    - Бот сопоставляет номер телефона с данными, ранее внесёнными Представителем управляющей компании, и связывает его учётную запись в MAX с записью в системе. Повторно этот шаг не требуется.
2. Перед жителем открывается меню с разделами: «Сообщить о проблеме», «Все обращения», «Перейти в чат дома», «Объявления», «Информация и контакты». Кнопка «Перейти в чат дома» показывается, если Представитель указал для дома ссылку-приглашение.
3. В разделе «Сообщить о проблеме» житель выбирает тему обращения (лифт, вода, отопление, электричество, подъезд, двор или другое); для аварийных ситуаций в этом же списке есть кнопка с телефонами аварийных служб. После выбора темы открывается мини-приложение с формой: место обнаружения (конкретный подъезд или весь дом), дата и время обнаружения проблемы, причина обращения (выбирается из списка для темы; для темы «Другое» вводится текстом), комментарий. Также житель может приложить фотографии (JPEG, PNG, WebP, GIF) для фиксации проблемы. (Смотрите альтернативный пользовательский сценарий, пункты 3.1 – 3.2).
4. После отправки обращение получает статус «принято» и становится видно диспетчеру дома (он получает сообщение от бота), а также другим жителям дома в разделе «Все обращения» (вкладки «Дом», «Подъезд», «Мои»), где они могут поддержать его лайком. Диспетчер видит обращения, отсортированные по числу лайков.
5. Диспетчер обрабатывает обращение и последовательно меняет его статус («принято» → «в работе» → «выполнено» или «отклонено»); комментарий при смене статуса обязателен. При каждом изменении статуса житель получает от бота сообщение с комментарием диспетчера; в мини-приложении отображаются текущий статус обращения и комментарии диспетчера. (Смотрите альтернативный пользовательский сценарий, пункт 5.1)
6. Житель получает уведомления в боте, когда диспетчер закрывает заявку и меняет статус обращения на «выполнено» (к такому комментарию диспетчер может приложить фото). Впоследствии житель может просмотреть выполненное обращение в архиве мини-приложения; отклонённые обращения остаются в общем списке.

**Альтернативный пользовательский сценарий**

3.1 Если по выбранной причине в том же подъезде (или, для обращения на весь дом, по всему дому) уже есть незакрытое обращение в статусе «принято» или «в работе», новое обращение не создаётся. Форма предлагает перейти к существующему обращению, чтобы поддержать его лайком вместо повторной подачи. Для причины «Другое» проверка не выполняется.

3.2 Если по выбранной причине для его подъезда или для всего дома в настоящий момент действует плановое уведомление (его создаёт диспетчер), создание обращения временно блокируется, так как проблема уже учтена в плановом порядке. Уведомление на весь дом блокирует обращения по любому подъезду, уведомление на подъезд — только обращения по этому подъезду. Диспетчер может отозвать уведомление досрочно. Для причины «Другое» проверка не выполняется.

5.1 Если диспетчер посчитал обращение не объективным, он переводит его в статус «отклонено» (из «принято» или «в работе») с обязательным комментарием, и житель получает уведомление с этим комментарием. Из статусов «выполнено» и «отклонено» возврата нет.

## 4. Архитектура

Решение состоит из четырёх частей, которые запускаются как отдельные контейнеры.

**Чат-бот в MAX** (Node.js, TypeScript, `@maxhub/max-bot-api`) — точка входа пользователя. Он показывает меню в зависимости от роли, привязывает аккаунт MAX к пользователю по номеру телефона, открывает мини-приложение и рассылает сообщения о новых обращениях, смене статуса и плановых уведомлениях. Действия в чате бот выполняет от имени пользователя, подтверждая себя общим секретом, известным только боту и backend.

**Backend** (Go, Gin, GORM) — единственный источник достоверных данных: пользователи, дома, обращения, история статусов, уведомления, реквизиты управляющей компании. Он предоставляет REST API, разделённый по ролям (Представитель УК, диспетчер, житель), и служебные эндпоинты для бота. Доступ в мини-приложение подтверждается токеном, который backend выдаёт после проверки подписи данных от MAX. При каждом запросе роль и активность пользователя проверяются по базе, поэтому отключение пользователя Представителем действует сразу. API описан спецификацией OpenAPI 3.1 ([openapi.yaml](openapi.yaml)); интерактивная страница доступна по адресу `/docs`.

**Мини-приложение** (React, Vite) — единый интерфейс для трёх ролей: набор экранов определяется тем, кто вошёл. Раздаётся через nginx, который также проксирует запросы к API.

**PostgreSQL** — основное хранилище данных. Схема применяется автоматически при каждом запуске backend. Загруженные фотографии хранятся в файловом томе backend.

**Взаимодействие частей.** Когда человек делится контактом, бот передаёт backend телефон и идентификатор MAX, и backend связывает их с пользователем, которого заранее завёл Представитель; незнакомый номер не привяжется. При открытии мини-приложения оно обменивает подписанные MAX данные на токен и использует его в каждом запросе. После значимых событий (создано обращение, сменился статус, опубликовано уведомление) backend асинхронно, без повторных попыток, отправляет их боту. Backend определяет, кого оповестить, бот определяет текст. Недоступность бота не мешает основному действию.

```
MAXITO/
├── bot/          чат-бот MAX
├── backend/      REST API
├── frontend/     мини-приложение
├── openapi.yaml  спецификация OpenAPI 3.1
├── DATA-API.yml  описание проверок API для автоматизированной оценки
└── docker-compose.yml
```

## 5. Запуск всех компонентов одной командой

```bash
cp .env.example .env   # заполнить обязательные параметры — раздел 6
docker compose up --build
```

Если токен бота на момент проверки недоступен, backend и мини-приложение работоспособны и без сервиса `bot`; недоступным в этом случае будет только вход через MAX (раздел 10). Docker Compose проверяет обязательные переменные для всего файла целиком, поэтому в `BOT_TOKEN` всё равно нужно указать любое значение-заглушку:

```bash
docker compose up --build postgres backend frontend
```

Работоспособность проверена: backend поднимается, применяет миграции и заполняет справочник тем и причин обращений, эндпоинт проверки состояния отвечает статусом «ok», мини-приложение доступно на порту 8081, запросы фронтенда к API корректно обрабатываются backend.

## 7. Переменные окружения

Корневой файл `.env` (рядом с `docker-compose.yml`) — единственный файл, который читает Docker Compose:

| Переменная            | Значение по умолчанию           | Назначение                                                                                         |
| --------------------- | ------------------------------- | -------------------------------------------------------------------------------------------------- |
| `BOT_TOKEN`           | не задано                       | Токен бота MAX (для сервиса `bot`)                                                                 |
| `MAX_INITDATA_SECRET` | не задано                       | Ключ проверки подписи данных MAX (для backend)                                                     |
| `JWT_SECRET`          | значение для локального запуска | Подпись токенов доступа, не менее 32 символов                                                      |
| `INTERNAL_API_KEY`    | значение для локального запуска | Общий секрет backend и bot                                                                         |
| `POSTGRES_PASSWORD`   | `postgres`                      | Пароль PostgreSQL (пользователь `postgres`, база `umniy_gorod`)                                    |
| `DEMO_CODE_WORD`      | пусто                           | Кодовое слово демо-входа; пусто — демо-режим выключен (раздел 12)                                  |
| `ALLOW_DEV_HEADERS`   | `false`                         | Отладочная авторизация заголовками (раздел 13); в демонстрационном окружении должна быть выключена |

Порты, режим `GIN_MODE`, параметры подключения к базе и `NOTIFY_URL` заданы в `docker-compose.yml` и через `.env` не меняются.

`backend/.env.example` — для запуска backend без Docker (`go run ./cmd/api`): параметры подключения к базе, порт и режим работы, а также:

- `UPLOAD_DIR` (по умолчанию `./uploads`) — каталог для фотографий к обращениям и фотографий-подтверждений диспетчера; в Docker это `/app/uploads`, подключённый постоянным томом.
- `JWT_SECRET`, `JWT_TTL_HOURS` (по умолчанию 720 часов, 30 суток) — подпись и срок действия токена доступа.
- `MAX_INITDATA_SECRET`, `INITDATA_MAX_AGE_SECONDS` (по умолчанию 86400 секунд, сутки) — проверка подписи и актуальности данных, полученных от MAX.
- `INTERNAL_API_KEY` — секрет для служебных эндпоинтов и рассылки уведомлений через бота.
- `ALLOW_DEV_HEADERS` (по умолчанию `false`) — при `true` допускает проверку REST API без подтверждения через MAX (раздел 13).
- `NOTIFY_URL` (по умолчанию `http://bot:3001/notify`) — адрес, по которому backend передаёт боту события для рассылки.

`bot/.env.example` — `BOT_TOKEN`, адрес backend `API_BASE_URL` (в контейнере подставляется автоматически), `INTERNAL_API_KEY` (совпадает со значением в backend), порт приёма уведомлений `NOTIFY_PORT` (по умолчанию 3001).

`frontend/.env.example` — параметры сборки Vite: `VITE_USE_MOCK` (`true` — демонстрационные данные в браузере без backend, `false` — реальный API; в Docker-сборке по умолчанию `false`), `VITE_API_BASE_URL` (по умолчанию `/api/v1`), `VITE_DEV_PHONE` (только для проверки реального API вне MAX).

## 8. Используемые порты

| Сервис           | Порт                             | Назначение                                                                                          |
| ---------------- | -------------------------------- | --------------------------------------------------------------------------------------------------- |
| frontend (nginx) | 8081 (на хосте)                  | Мини-приложение «На виду»; также проксирует `/api/`, `/uploads/`, `/docs` и `/api-docs/` на backend |
| backend          | 8080 (только внутри сети Docker) | REST API, проверка состояния `/health`, статика загруженных файлов                                  |
| postgres         | 5432 (только внутри сети Docker) | База данных                                                                                         |
| bot              | 3001 (только внутри сети Docker) | Приём уведомлений от backend                                                                        |

Backend, PostgreSQL и бот порты на хост не публикуют: API снаружи доступен через порт 8081 по путям `/api/v1/...`. Бот обращается к MAX Bot API как клиент.

## 9. Зависимости

- bot: Node.js 24, pnpm, `@maxhub/max-bot-api`, `zod`, `ofetch`, `dotenv`.
- backend: Go 1.25+ (образ сборки — Go 1.26), `gin-gonic/gin`, `gorm.io/gorm`, `gorm.io/driver/postgres`, `golang-jwt/jwt/v5`, `joho/godotenv`.
- frontend: React 18, Vite 5, TypeScript 5, без дополнительных библиотек интерфейса.
- Инфраструктура: PostgreSQL 18, nginx 1.27 (обслуживание статики и обратное проксирование запросов).

## 10. Внешние сервисы и интеграции

Единственный внешний сервис, необходимый для полного прохождения основного сценария и невоспроизводимый внутри Docker, — платформа MAX (Bot API и Mini Apps). Взаимодействие с платформой двустороннее: мини-приложение получает от MAX подписанные данные о пользователе и обменивает их на токен доступа backend; backend, в свою очередь, уведомляет бота о новых обращениях, изменении статуса и публикации плановых уведомлений, а бот рассылает соответствующие сообщения пользователям.

Ссылка на зарегистрированного бота в MAX: **\_** (заполняется перед демонстрацией).

**Проверка backend и мини-приложения без MAX.** Такая проверка позволяет оценить логику решения, но не саму интеграцию с платформой. Мини-приложение можно открыть в обычном браузере на порту 8081. Запросы к REST API можно выполнять напрямую (через `http://localhost:8081/api/v1/...`), если в `.env` включён `ALLOW_DEV_HEADERS=true` — тогда подтверждение личности заголовками временно заменяет проверку подписи данных MAX (раздел 13). В демонстрационном окружении этот параметр должен быть выключен.

## 11. Работа с данными

- Основное хранилище данных решения — PostgreSQL; структура базы данных применяется автоматически при каждом запуске backend. В базе хранятся фамилия, имя, отчество и номер телефона жителей и диспетчеров; персональные данные обрабатываются в объёме, необходимом для идентификации пользователя в чат-боте, в соответствии с Федеральным законом № 152-ФЗ «О персональных данных».
- Фотографии, приложенные к обращению жителя, и фотографии-подтверждения диспетчера хранятся в каталоге `/app/uploads` контейнера backend, который подключён постоянным томом `uploads_data`, и передаются пользователю по прямой ссылке.
- Справочник тем и причин обращений, включая признак пригодности причины для планового уведомления, формируется автоматически при запуске backend и не редактируется через API в процессе работы.
- Реквизиты управляющей компании представлены одной записью на весь развёрнутый экземпляр решения; список аварийных служб общий для всех домов управляющей компании.
- Данные о домах, жителях, диспетчерах и обращениях вносятся только через интерфейсы Представителя, диспетчера и чат-бота. Исключение — демонстрационный дом с примерами обращений и планового уведомления, который создаётся, только если задан `DEMO_CODE_WORD` (раздел 12).
- Для пользователей, домов, жителей и обращений применяется мягкое удаление: исторические записи не удаляются физически. История изменения статуса обращения не подлежит редактированию.

## 12. Порядок работы с тестовыми данными

По умолчанию backend не создаёт демонстрационных пользователей, домов или обращений — автоматически формируется только справочник тем и причин (раздел 11). Есть два способа получить рабочие данные.

**Демо-режим по кодовому слову.** Предназначен для проверки развёрнутого бота без предварительной регистрации в системе. Если в `.env` backend задан `DEMO_CODE_WORD`, при запуске создаётся общий демо-дом («Демо-дом для проверки API», 3 подъезда) с примерами обращений и плановым уведомлением. Любой человек, знающий кодовое слово, может получить в этом доме доступ в любой из трёх ролей; подробный порядок действий — в разделе 13. Для аккаунтов, созданных таким образом, в меню бота доступна кнопка «Сменить роль». После проверки переменную нужно убрать из `.env` и перезапустить backend: демо-режим выключится, вход по кодовому слову перестанет работать.

**Ручное создание Представителя.** Роль Представителя управляющей компании не может быть зарегистрирована самостоятельно (раздел 15), поэтому первую запись вносят вручную:

```bash
# выполняется один раз после первого запуска, пока база данных пустая
docker compose exec postgres psql -U postgres -d umniy_gorod -c "INSERT INTO users
  (phone, full_name, role, is_active, created_at, updated_at)
  VALUES ('+70000000001', 'Тестовый Представитель', 'representative', true, now(), now());"
```

Дальнейшие действия выполняются либо через бота (действительная привязка контакта), либо напрямую через REST API при включённом `ALLOW_DEV_HEADERS` (раздел 13).

**Демонстрационный режим без backend.** Мини-приложение может работать автономно, на заранее подготовленных тестовых данных (обращения во всех статусах, несколько плановых уведомлений, несколько домов); режим включается параметром сборки `VITE_USE_MOCK=true` и хранит данные в браузере, что удобно для демонстрации интерфейса без развёртывания базы данных.

## 13. Пошаговый сценарий проверки

**Вариант А. Проверка развёрнутого бота (демо-режим).** Разворачивать ничего не нужно, достаточно аккаунта в MAX, ссылки на бота (раздел 10) и кодового слова. Кодовое слово передаётся проверяющим отдельно (в служебных данных сдачи), в репозитории оно не хранится.

1. Открыть бота по ссылке и нажать «Начать» (или отправить любое сообщение). Бот предложит поделиться номером телефона.
2. **Не отправлять свой номер** — его нет в системе, и бот ответит, что номер не найден. Вместо этого нажать кнопку «Ввести кодовое слово».
3. Ввести кодовое слово сообщением. При ошибке бот сообщит о неверном слове, при отключённом демо-режиме — что режим выключен.
4. Выбрать роль кнопкой: «Житель», «Диспетчер» или «Представитель».
5. Ввести ФИО, затем номер телефона в формате `+7...`. Номер любой и в базе не проверяется; он не должен принадлежать реальному пользователю системы, иначе бот попросит ввести другой.
6. После сообщения «Демо-доступ выдан» откроется меню выбранной роли. Пользователь привязан к общему демо-дому: житель — подъезд 1, диспетчер закреплён за этим домом, Представитель видит все дома.
7. **Сценарий жителя.** «Сообщить о проблеме» → выбрать тему → в открывшемся мини-приложении заполнить форму и отправить. Для получения нового обращения без срабатывания защиты от дублей и блокировки уведомлением выбрать причину не из демо-примеров, например тему «Двор» или «Другое». В демо-доме уже есть незакрытое обращение по лифту («не работает / стоит») и плановое уведомление по этой же причине: попытка создать такое обращение покажет альтернативный сценарий 3.1 или 3.2 (раздел 3): дубль либо блокировку уведомлением.
8. **Сценарий диспетчера.** Нажать «Сменить роль» → «Диспетчер» (либо войти вторым аккаунтом MAX). «Обращения» откроет мини-приложение, где созданное обращение переводится в «в работе» и затем в «выполнено» или «отклонено» с комментарием. Доступны также «Горячие обращения», «Статистика по домам» и «Уведомления» (публикация планового уведомления).
9. Вернуться в роль жителя («Сменить роль» → «Житель»): бот пришлёт сообщение о смене статуса с комментарием, а в мини-приложении будет виден новый статус.
10. **Сценарий Представителя.** «Сменить роль» → «Представитель»: загрузка домов, диспетчеров и жителей из CSV, назначение домов, реквизиты УК, аварийные службы. Шаблоны CSV бот присылает по запросу в соответствующем пункте меню.

**Вариант Б. Собственный запуск с демо-режимом (требуется бот в MAX).**

1. Скопировать `.env.example` в `.env`, задать `BOT_TOKEN`, `MAX_INITDATA_SECRET` (раздел 6) и `DEMO_CODE_WORD`.
2. Выполнить `docker compose up --build`.
3. Дальше действовать по пунктам 1–10 варианта А.

**Вариант В. REST API без MAX (отладочная авторизация заголовками).**

1. Скопировать `.env.example` в `.env`, задать `BOT_TOKEN` (можно заглушку), `MAX_INITDATA_SECRET` (раздел 6) и `ALLOW_DEV_HEADERS=true`.
2. Выполнить `docker compose up --build postgres backend frontend` и дождаться запуска контейнера backend.
3. Проверить работоспособность backend: `docker compose exec backend wget -qO- http://localhost:8080/health` должно вернуть статус «ok».
4. Внести тестового Представителя (раздел 12).
5. Получить доступ Представителя для дальнейших запросов: backend свяжет идентификатор пользователя при первом запросе с указанными заголовками:

```bash
curl -H "X-Max-User-Id: demo-rep" -H "X-Max-User-Phone: +70000000001" \
  http://localhost:8081/api/v1/me
```

6. Создать дом (адрес указан латиницей, поскольку ввод кириллицы в команде `curl` на Windows искажает кодировку; сам API кириллицу принимает корректно):

```bash
curl -X POST -H "X-Max-User-Id: demo-rep" -H "Content-Type: application/json" \
  -d '{"address":"Test Street, 1","number":"1","entrances_count":4}' \
  http://localhost:8081/api/v1/representative/houses
```

7. Открыть мини-приложение на порту 8081 в браузере и оценить интерфейс. Полная проверка авторизации через реальный API требует MAX (раздел 10).
8. Для демонстрации интерфейса без выполнения пунктов 4–6 допускается локальный запуск фронтенда в режиме демонстрационных данных (раздел 12), без Docker и backend.

Для проверки основного пользовательского сценария внутри самого MAX необходимо открыть зарегистрированного бота по ссылке из раздела 10 и пройти путь, описанный в разделе 3: передать контакт, открыть мини-приложение, создать обращение.

## 14. Примеры ожидаемого поведения системы

- Повторное обращение по той же причине в том же подъезде дома, пока предыдущее не закрыто, не создаётся: система возвращает ошибку с указанием идентификатора уже существующего обращения, а мини-приложение предлагает поддержать его лайком.
- Изменение статуса обращения без комментария диспетчера отклоняется системой с ошибкой.
- Недопустимый переход статуса, например попытка изменить уже выполненное обращение, отклоняется: такой статус является конечным.
- Фотография-подтверждение принимается системой только при переводе обращения в статус «выполнено»; при любом другом статусе запрос с фотографией отклоняется.
- Попытка жителя поддержать лайком собственное обращение отклоняется; повторная попытка поддержать лайком уже поддержанное обращение также отклоняется.
- При действующем плановом уведомлении по той же причине на тот же подъезд (или на весь дом) создание нового обращения временно блокируется; причины, не отмеченные как пригодные для планового уведомления, никогда не становятся основанием для такой блокировки.
- Указание номера подъезда, отсутствующего в доме, отклоняется системой — как при создании обращения и уведомления, так и при загрузке списка жителей.
- Попытка диспетчера опубликовать плановое уведомление с причиной, не предназначенной для таких уведомлений, отклоняется системой независимо от способа отправки запроса.
- Доступ пользователя, отключённого Представителем управляющей компании, прекращается непосредственно со следующего запроса, не дожидаясь истечения срока действия токена.
- Данные, полученные от MAX с нарушенной или устаревшей подписью, отклоняются системой; если подпись верна, но контакт пользователя ещё не привязан к учётной записи, система сообщает о необходимости выполнить привязку через бота.

## 15. Известные ограничения

- Роль «Представитель управляющей компании» не может быть зарегистрирована самостоятельно: первая запись вносится администратором вручную (раздел 12) либо создаётся в демо-режиме. Это осознанное решение в рамках MVP, соответствующее тому, что данная роль представляет саму управляющую компанию, а не отдельного независимого пользователя (раздел 2).
- Ведение свободной переписки по обращению вне смены его статуса не реализовано: комментарий существует только как часть изменения статуса обращения.
- Нет интеграции с ГИС ЖКХ: данные о домах, жителях и диспетчерах вносит Представитель.
- Групповой чат дома не создаётся автоматически (ограничение Bot API MAX): жителям выдаётся ссылка-приглашение, которую вносит Представитель.
- Сменность диспетчеров упрощена: за домом закрепляется один или несколько диспетчеров без графика дежурств.
- Контакты аварийных служб можно только загрузить CSV-файлом; редактирование и удаление отдельной записи не предусмотрено.
- Уведомления бота отправляются без повторных попыток: если бот в этот момент недоступен, сообщение не будет доставлено.

## 16. Остановка и повторный запуск

```bash
docker compose down       # остановить и удалить контейнеры; данные БД и загруженные файлы сохраняются в томах
docker compose down -v    # дополнительно удалить тома (полный сброс, включая загруженные фотографии)
docker compose up --build # запустить решение заново (без -v данные сохраняются)
```
