# Умный город — Описание проекта (MVP)

**Чат-бот + мини-приложения в MAX для управления обращениями жителей многоквартирного дома**

Документ подготовлен на основе описания команды, анализа официальных источников (59-ФЗ, Правила предоставления коммунальных услуг № 354, Порядок информационного взаимодействия через сервис MAX / ГИС ЖКХ) и требований кейса хакатона «Умный город».

---

## 1. Функционал проекта по ролям и этапам

### 1.1. Общая концепция

Продукт — это чат-бот в мессенджере MAX с подключёнными мини-приложениями, который решает задачу структурированной подачи, обработки и отслеживания обращений жителей многоквартирного дома (МКД) по вопросам содержания общего имущества и качества коммунальных услуг.

**Границы решения:**
- Один экземпляр продукта рассчитан на **одну управляющую компанию (УК)**.
- Внутри УК может быть несколько домов.
- Данные домов разных УК не пересекаются.
- Основной приоритетный сценарий: «Житель фиксирует проблему → получает структурированное обращение и статус → диспетчер работает с подготовленной карточкой».

**Ключевые принципы:**
- Максимальная структурированность данных (мини-аппы с шаблонными полями).
- Прозрачность статуса для жителя.
- Снижение количества необоснованных и дублирующих обращений.
- Опора на существующие обязанности УК и сроки рассмотрения обращений (59-ФЗ).

---

### 1.2. Роли

#### Роль 1. Представитель управляющей компании
Самый первый пользователь системы от лица УК.

**Как появляется:**
- Решение передаётся уже проверенной управляющей компании.
- Представитель регистрируется первым: вводит ФИО.
- Система запоминает номер телефона.
- При повторном входе (если чат был удалён) — авторизация по номеру телефона.

**Основной функционал:**
- Добавление и удаление диспетчеров.
- Добавление диспетчера: ФИО + номер телефона.
- Возможность массового добавления диспетчеров через загрузку файла (CSV/Excel).

**Ограничения роли:**
- Не работает напрямую с обращениями жителей.
- Не создаёт дома и не регистрирует жителей (это делает диспетчер).

#### Роль 2. Диспетчер
Сотрудник УК, ответственный за один или несколько домов.

**Как появляется:**
- Добавляется Представителем.
- Авторизуется в боте по номеру телефона.

**Основные возможности:**

1. **Управление домами**
   - Добавить дом в свою зону ответственности (кнопка «Добавить дом»).
   - Указать минимальные данные дома (адрес / номер дома).
   - После создания дома в системе появляется `house_id`, вокруг которого строится вся дальнейшая работа.
   - Снять дом со своей ответственности (дом при этом остаётся в системе УК).
   - Несколько диспетчеров могут быть ответственными за одни и те же дома (учёт сменности без сложной логики дежурств).

2. **Регистрация жителей**
   - После создания дома диспетчер загружает список жителей (ФИО + номер телефона) через CSV/Excel.
   - Источник списка — данные лицевых счетов и договоров УК (сбор этих данных не входит в границы продукта).
   - После загрузки и подтверждения жителям открывается функционал бота.

3. **Работа с обращениями**
   - Просмотр обращений по конкретному дому.
   - Сортировка и приоритизация с учётом количества подписок (лайков) от жителей.
   - Изменение статуса обращения (Принято → В работе → Нужна дополнительная информация → Выполнено / Отклонено и т.д.).
   - Получение уже структурированной карточки обращения (тип, описание, дата, место, контакты жителя).

4. **Уведомления жителей**
   - Отправка уведомлений о плановых отключениях (вода, электричество, лифт и т.д.).
   - Уведомления используются системой для автоматической блокировки необоснованных обращений в период действия уведомления.

#### Роль 3. Житель
Основной пользователь продукта.

**Как появляется:**
- Диспетчер загружает его данные (ФИО + телефон) при регистрации дома.
- После подтверждения создания дома жителю становится доступен функционал бота.
- Авторизация / идентификация — по номеру телефона.

**Главное меню жителя:**
1. Сообщить о проблеме
2. Все заявления (обращения)
3. Уведомления от диспетчера
4. Информация и контакты
5. Общий чат дома (через ссылку-приглашение)

---

### 1.3. Детальный сценарий «Сообщить о проблеме» (ядро MVP)

1. Житель выбирает пункт «Сообщить о проблеме».
2. Бот предлагает выбрать тип проблемы:
   - Не работает лифт
   - Не убран двор / подъезд
   - Отключено электричество
   - Прорвало трубу / затопление
   - Проблемы с отоплением
   - Проблемы с водой (нет / слабый напор / качество)
   - Другое
3. При выборе критичных типов (прорыв трубы, газ, застревание в лифте) бот **сначала** показывает кнопку «Позвонить в аварийно-диспетчерскую службу» с актуальным номером, и только потом предлагает зафиксировать обращение.
4. Открывается мини-приложение с формой.
5. Поля формы:
   - Тип проблемы (заполняется автоматически)
   - Подъезд / этаж / место
   - Описание (текст с ограничением длины)
   - Дата и время обнаружения
   - Важность: «Обычная» / «Важная» (слово «срочно» не используется)
   - Чекбокс «Хочу перерасчёт» (для проблем качества услуг)
   - Возможность прикрепить фото/видео (в MVP можно отложить, но заложить в интерфейс)
6. Система проверяет:
   - Есть ли активное уведомление от диспетчера по этой теме на текущий период → если есть, отправка блокируется с объяснением.
   - Есть ли уже похожее открытое обращение от другого жителя → предлагается подписаться (поставить «лайк») вместо создания дубля.
7. После успешной отправки житель получает номер обращения и информацию о сроках рассмотрения (ориентир на 30 дней согласно 59-ФЗ).
8. Обращение появляется в разделе «Все заявления» и у диспетчера.

**Система подписок (лайков):**
- Житель может подписываться под обращениями других жителей.
- Количество подписок влияет на сортировку и приоритет для диспетчера.
- Это замена классическим коллективным обращениям — более простая и прозрачная механика.

### 1.4. Раздел «Все заявления»

- Житель видит список обращений своего дома.
- Возможность фильтра: «Мои» / «Все».
- Каждое обращение отображается в виде карточки:
  - Тип проблемы
  - Дата
  - Краткий комментарий
  - Текущий статус (обязательно виден жителю)
  - Количество подписок
  - Кнопка «Подписаться»
- Статусы обращения (минимум):
  - Принято
  - В работе
  - Нужна дополнительная информация
  - Выполнено
  - Отклонено / Закрыто

### 1.5. Уведомления от диспетчера

- Отображаются в мини-приложении (история + детали).
- В главном меню бота — индикатор новых уведомлений.
- Используются для автоматической фильтрации необоснованных обращений.

### 1.6. Информация и контакты

Отдельный пункт меню:
- Название управляющей компании
- Телефон аварийно-диспетчерской службы (самый важный)
- Контакты диспетчера / режим работы
- Краткая памятка «Ваши права при обращении» (выдержки из 59-ФЗ и Правил № 354)

### 1.7. Общий чат дома

- Реализуется через ссылку-приглашение, которую создаёт диспетчер (или старший по дому) вручную один раз.
- Бот хранит и выдаёт эту ссылку.
- Автоматическое создание группы и массовое добавление участников ботом на текущий момент API MAX ограничено и ненадёжно — поэтому выбран безопасный вариант.

## 2. Моменты, важные для выполнения требований кейса

### 2.1. Соответствие тематике и рекомендациям

| Требование кейса | Как выполняем |
|------------------|---------------|
| Конкретный пользователь и контекст | Житель МКД, обслуживаемого УК, который хочет зафиксировать проблему по содержанию дома или качеству коммунальных услуг и отслеживать статус |
| Подтверждение актуальности проблемы | Опираемся на 59-ФЗ (сроки 30 дней, право на ответ по существу, регистрация за 3 дня), Правила № 354 (качество услуг, перерасчёт, границы ответственности), Порядок информационного взаимодействия через MAX/ГИС ЖКХ (2025–2026) |
| Один приоритетный сценарий | «Сообщить о проблеме → структурированная форма → статус → работа диспетчера» |
| MAX как основная среда | Весь основной сценарий проходит в чат-боте + мини-приложениях MAX |
| Мини-приложение подключено к боту | Да, формы обращений и уведомления реализованы как мини-аппы |
| Тестовые данные | Если нет реальной интеграции с ГИС ЖКХ — явно указываем в README и презентации |
| Собственный API | Есть (бэкенд на Gin). Не даёт дополнительных баллов, но требует выполнения требований к OpenAPI и DATA-API.yaml при сдаче |

### 2.2. Ожидаемый эффект (нужно будет чётко прописать)

Примеры измеримых показателей, которые можно заявить:

- Сокращение времени на подачу корректного обращения.
- Снижение доли дублирующих / необоснованных обращений.
- Рост доли обращений, по которым житель видит актуальный статус.
- Увеличение доли обращений, рассмотренных в установленный 59-ФЗ срок (за счёт лучшей структурированности входящих данных).

### 2.3. Масштабирование

- Решение рассчитано на одну УК.
- При переносе в другую УК нужно: создать нового Представителя, добавить диспетчеров, загрузить дома и списки жителей.
- Логика бота, статусов, форм и подписок остаётся неизменной.
- При появлении реальной интеграции с ГИС ЖКХ / сервисом обмена информацией — можно будет автоматически подтягивать часть данных.

## 3. Сильные и слабые стороны проекта

### Сильные стороны

- Чёткий фокус на одной реальной боли (структурирование и прозрачность обращений).
- Хорошее соответствие приоритетному направлению кейса («Аварии, заявки и коммунальные услуги»).
- Опора на действующее законодательство (59-ФЗ, Правила 354, документы Минстроя по MAX).
- Механики снижения мусорных обращений (блокировка по уведомлениям + подписки вместо дублей).
- Прозрачный статус для жителя (обязательное требование команды).
- Разделение ролей, близкое к реальной работе УК.
- Технически реализуемо в рамках хакатона (чат-бот + мини-аппы + свой бэкенд).

### Слабые стороны и риски

- Автоматическое создание группового чата жителей ограничено возможностями текущего Bot API MAX.
- Нет реальной интеграции с ГИС ЖКХ (нужно честно обозначать использование тестовых данных).
- Роль «Представитель» — внутренняя роль продукта, её нужно аккуратно объяснить относительно реальных должностей в УК.
- Загрузка списка жителей зависит от качества данных, которые есть у УК.
- Сменность диспетчеров упрощена (несколько диспетчеров на одни дома вместо полноценного графика дежурств).
- Пока нет загрузки фото/видео в MVP (желательно заложить хотя бы интерфейсно).

## 4. Что обязательно нужно доделать или улучшить

### Критично до сдачи MVP

1. **Зафиксировать формулировку проблемы и целевого пользователя** с отсылками к официальным источникам.
2. **Прописать 2–3 чётких метрики ожидаемого эффекта**.
3. **Реализовать обязательное отображение статуса** обращения для жителя.
4. **Сделать сортировку обращений для диспетчера** с учётом количества подписок.
5. **Реализовать проверку на активные уведомления** при создании обращения.
6. **Реализовать предложение подписаться** под существующим похожим обращением.
7. **Групповой чат** — только через ссылку-приглашение (не пытаться создавать группу ботом автоматически).
8. **Явно указать** в README и презентации, что данные тестовые / смоделированные (если нет реальной интеграции).
9. **Подготовить демо-дом** с уже зарегистрированными жителями и диспетчером для удобной проверки экспертами хакатона.

### Желательно (если останется время)

- Базовая загрузка фото к обращению.
- История изменения статусов.
- Простая памятка «Ваши права» с выдержками из 59-ФЗ и Правил 354.
- Возможность жителю добавить комментарий / уточнение к своему обращению.

### Можно отложить

- Полноценная сменность диспетчеров.
- Интеграция с ГИС ЖКХ.
- Сложный ИИ-анализ текста обращений.
- Голосовой ввод.

## Краткий итог

Проект имеет хороший потенциал для хакатона: он решает реальную и приоритетную проблему, опирается на действующие нормы, имеет понятный сквозной сценарий и измеримый эффект.  

Главное сейчас — максимально жёстко сфокусироваться на ядре (структурированное обращение + статус + борьба с дублями), честно обозначить тестовые данные и подготовить удобный демо-режим для экспертов.

Документ можно использовать как основу для README.md, описания в презентации и внутреннего технического задания команды.
